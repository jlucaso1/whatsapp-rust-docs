title: "June 9, 2026 — Device list: primary device preserved on identity rotation"
description: "Fixed a bug where a companion relink or identity rotation could silently drop device 0 from the stored device list, preventing encrypted messages from reaching the primary phone."
---

## Fixes

**Device list always retains primary after identity rotation ([#797](https://github.com/oxidezap/whatsapp-rust/pull/797))**

When a device-add notification carried a `key-index-list` whose `raw_id` differed from the stored one (an identity rotation or companion relink), `patch_device_add` cleared the device list and rebuilt it from the notification. Because `filter_devices_by_key_index` only keeps device 0 when it is already present in the input, the primary was silently dropped after the clear — leaving a record such as `[{device_id: 19}]` (no primary) or even an empty list when the notified device's key index was rejected.

`get_user_devices` treats any existing record as authoritative and only fetches from the network when there is **no** record at all, so the bad list would persist indefinitely and the self-healing usync re-fetch would never fire. All subsequent encrypted sends to that user would skip the primary phone.

The fix mirrors WA Web's `WAWebHandleAdvDeviceNotificationApi.handleDeviceAddNotification`, which unconditionally re-adds `{ id: DEFAULT_DEVICE_ID, keyIndex: 0 }` to the rebuilt list (whatsmeow keeps the same invariant). `patch_device_add` now ensures device 0 is present after every rebuild, so an identity rotation can never produce a device set that excludes the primary.

**Impact:** Users whose contacts performed a companion relink or identity rotation during an active session could silently lose message delivery to those contacts' primary phones until the next full usync. No API changes, no breaking changes.
