## Performance

**Write-behind buffer for `messageSecret` persistence ([#831](https://github.com/oxidezap/whatsapp-rust/pull/831))**

Every inbound message carrying a `messageSecret` (polls, events, bot prompts, and any secret-bearing text under the default `Managed` policy) previously paid a synchronous SQLite upsert inside the per-chat receive lane, before the server ack and before `Event::Message` was dispatched. During an offline drain or a group fan-in burst this was one transaction per message on the critical path.

**New `MsgSecretWriteBuffer`.** A write-behind buffer splits visibility from durability:

- **Capture** inserts into an in-memory pending map synchronously (no `await`), so the per-chat lane ordering guarantee is preserved by construction. A detached drain task is then scheduled.
- **Drain** batches everything pending into one `put_msg_secrets` call, looping until empty. A burst of captures coalesces into a single transaction.
- **Reads** check the buffer before the store in every lookup path — primary, LID/PN alternate, msmsg bot-reply, and addon send — so a not-yet-flushed secret is never invisible.
- **Entries leave the buffer only after the backend write returns**, so a reader always finds a secret either pending or persisted, never neither.
- **Graceful shutdown** calls `seal()` then `flush()` during `disconnect()`. After sealing, any straggler `queue()` call writes inline (synchronous semantics) before returning, so a lane worker still draining its backlog cannot strand a secret on the detached drain after the final flush.

The outbound send-time secret store (`persist_outbound_msg_secret`) goes through the same buffer, and msmsg bot-reply reads check it first, covering the send-path gap.

**Durability tradeoff.** The window between server ack and the drain task flushing can lose secrets on a process crash (recoverable via the app resolver). WhatsApp Web has the same window — its IndexedDB persistence is asynchronous too.

**No breaking changes.** All API surfaces are unchanged.
